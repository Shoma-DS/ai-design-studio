# UI/UX設計と品質検査

「どのUIパターンを使うか」は `skills/design/ui-pattern-dictionary/SKILL.md`（108パターンの辞典）。
このスキルは **そのパターンを正しく成立させ、体験として機能させるための基準と検査**を扱う。

## いつ使うか

| 場面 | 使うセクション |
|---|---|
| LP/HP/スワイプLPの構成を決める前 | 1. UX層の設計 |
| ワイヤー・原稿ができた時点 | 2. 評価軸 / 8. 目視チェック |
| 実装・画像生成が終わった時点 | 3〜6. 数値基準 → 7. 実測監査 |
| 納品前 | 7. 実測監査 + 8. 目視チェック（必須） |
| 既存サイトのLP診断・改善提案案件 | 7 → 8 → 9. 提案の書き方 |

HTML実装があるもの（HP、ハイブリッドLP、スワイプLP、ギャラリー）は **7の実測監査を必ず通す**。
1枚絵のラスターLPは監査スクリプトが使えないので、3〜4の数値基準を画像プロンプトと構図の段階で満たしにいく。

## 0. 前提: デザインの4原則がUIで何に化けるか

| 原則 | UIでの現れ方 | 崩れたときの症状 |
|---|---|---|
| 近接 | 関連要素の間隔 < グループ間の間隔（比率1:2以上） | 「どの見出しがどの本文か」が一瞬わからない |
| 整列 | 左揃えの軸を通す。中央揃えは短い見出しだけ | 要素がふわふわ浮いて素人っぽく見える |
| 反復 | 色・書体・角丸・余白・アイコン様式・影の一貫 | 同じ意味の要素が場所ごとに違う顔をする |
| コントラスト | ジャンプ率・色・太さの差を「はっきり」つける | 全部同じ強さ＝どこも見ない画面になる |

**4原則の判定基準**: 迷ったら「差は2倍以上つけるか、完全に揃えるか」。中間が一番弱い。

## 1. UX層の設計（構成を決める前に埋める）

### 1-1 前提の言語化

制作物ごとに、この5行を先に埋める。埋まらないまま構成に入ると、あとで全部やり直しになる。

```text
・誰が: （属性ではなく状況で書く。例「産後1年、自分の服が入らなくなった30代」）
・どんな状態で見るか: （移動中スマホ / 夜の比較検討 / 広告からの初訪問）
・何を得たいか: （情報 or 安心 or 決断の後押し）
・離脱する理由: （高い / 怪しい / 面倒 / 自分向けじゃない のどれか）
・このページのゴール1つ: （予約 / 資料DL / LINE登録）
```

「離脱する理由」がそのままセクション構成の必要項目になる。高い→料金の内訳と保証、怪しい→実績と顔出し、面倒→所要時間とステップ数、自分向けじゃない→対象者の明示。

### 1-2 認知の法則（構成判断に効くものだけ）

| 法則 | 制作上の意味 |
|---|---|
| ヤコブの法則 | ユーザーは他サイトでの慣れを持ち込む。ナビ・カート・CTAの位置で奇をてらわない |
| ヒックの法則 | 選択肢が増えるほど決定が遅れる。プランは3つまで、CTAは1画面1種類 |
| フィッツの法則 | 押させたいものは「大きく・近く」。スマホは親指の届く下部が最短距離 |
| ミラーの法則 | 並列情報は4〜6個で区切る。特徴9個の羅列より3×3のグループ |
| ドハティのしきい値 | 反応が400msを超えると「待たされた」になる。ホバーや開閉は150〜300ms |
| ピーク・エンドの法則 | 体験の記憶は「山場」と「終わり」で決まる。最終セクションとサンクスページを雑にしない |
| フォン・レストルフ効果 | 目立たせたいものは1つだけ色や形を変える。全部強調は無強調と同じ |
| 系列位置効果 | 最初と最後が記憶に残る。最重要の訴求を冒頭とラストに置く |

### 1-3 情報の順序（LPの標準骨格）

つかみ → 共感（現状の課題）→ 原因の提示 → 解決策 → 根拠（実績・数値・声）→ 具体像（流れ・内容）→ 不安の解消（保証・FAQ）→ 行動（CTA）。

セクション別のテンプレは `skills/design/lp-layout-templates/SKILL.md` の4種類を先に確認する。

## 2. 評価軸: ニールセンの10ヒューリスティック

既存サイトの診断や、自作の粗探しはこの10項目で網羅的に見る。

| # | 原則 | LP/HPでの具体 |
|---|---|---|
| 1 | システム状態の可視化 | 送信中のボタン状態、読み込み、フォームの進捗（3ステップ中2） |
| 2 | 現実世界との一致 | 専門用語より利用者の言葉。「コンバージョン」ではなく「お問い合わせ」 |
| 3 | ユーザーの主導権と自由 | 閉じられるモーダル、戻れるステップ、自動再生の停止 |
| 4 | 一貫性と標準 | 同じ役割のボタンは同じ見た目。ロゴは常にトップへ戻る |
| 5 | エラーの予防 | 必須項目の事前明示、入力形式の例示、破壊的操作の確認 |
| 6 | 記憶より認識 | 前ページの内容を覚えさせない。確認画面に入力値を全部出す |
| 7 | 柔軟性と効率 | 電話タップ発信、LINE導線、autocomplete対応 |
| 8 | 美的で最小限のデザイン | 1画面1メッセージ。装飾が情報を上回らない |
| 9 | エラーからの回復 | 何がどう間違いか＋直し方を、該当フィールドの隣に日本語で |
| 10 | ヘルプとドキュメント | FAQ、所要時間、キャンセル条件を探させない位置に置く |

## 3. UIの数値基準

### 3-1 タイポグラフィ

| 項目 | 基準 |
|---|---|
| 本文サイズ | スマホ16px（最低15px）、PC16〜17px。注釈は12pxを下限 |
| 行間 | 日本語本文 1.7〜1.9 / 見出し 1.2〜1.4（長いほど広く） |
| 一行の文字数 | 日本語20〜45字、欧文45〜90字。超えたら`max-width`で止める |
| 字間 | 日本語見出しは -0.02em 〜 0.04em。欧文大文字は 0.04〜0.1em |
| ジャンプ率 | 見出し÷本文 = 1.5〜2.5倍。中途半端な1.2倍は「ミス」に見える |
| 書体数 | 2種（見出し・本文）。多くて3種 |
| ウェイト | 使うのは2〜3段階（例 400/700）。細かい差は環境で潰れる |
| 禁則 | 日本語は `word-break: normal; overflow-wrap: anywhere;` 単語途中改行を避ける |

### 3-2 余白とレイアウト

| 項目 | 基準 |
|---|---|
| スペーシング | 4pxまたは8pxの倍数（4/8/12/16/24/32/48/64/96） |
| 近接の比率 | グループ内の間隔 : グループ間の間隔 = 1 : 2 以上 |
| セクション間 | スマホ 56〜80px / PC 96〜160px |
| 左右余白 | スマホ 20〜24px。画面端に文字を寄せない |
| コンテナ幅 | 本文主体1000〜1200px。カード並列は最大1200px |
| カラム | 3カラムはPC限定。スマホは1カラムに落とす |

### 3-3 色

| 項目 | 基準 |
|---|---|
| 配分 | 背景・ベース60% / メイン30% / アクセント10%（アクセントはCTAに集中させる） |
| コントラスト | 本文 4.5:1以上、24px以上または太字18.66px以上は 3:1以上（WCAG AA） |
| 意味色 | 成功=緑 / 警告=黄 / エラー=赤 / 情報=青。ブランド色と衝突させない |
| 色だけに頼らない | エラーは赤字＋アイコン＋文言。色覚特性で判別できない場合がある |

パレット生成とコントラスト計算は `skills/design/color-palette-generator/SKILL.md`。

### 3-4 操作領域

| 項目 | 基準 |
|---|---|
| タップ領域 | 44×44px以上（iOS HIG）。最低でも24×24px（WCAG 2.2 AA） |
| 隣接間隔 | タップ要素どうしは8px以上離す |
| 親指ゾーン | スマホの主要CTAは画面下1/3。上部に置くなら追従バーで補う |
| 入力欄 | `font-size: 16px`以上（iOS Safariの自動ズーム回避） |
| カーソル | クリック可能な要素は `cursor: pointer`、無効は `not-allowed` |

### 3-5 モーション

| 項目 | 基準 |
|---|---|
| UI反応（ホバー・押下） | 100〜200ms |
| 開閉・出現 | 200〜300ms |
| 画面遷移・大きな動き | 300〜500ms（500ms超は待たされる） |
| イージング | 出現 `cubic-bezier(.16,1,.3,1)` 系 / 消失は速く |
| 同時に動かす数 | 1画面で同時に動くのは3要素まで。順次表示はstagger 60〜100ms |
| 配慮 | `@media (prefers-reduced-motion: reduce)` でアニメーションを止める |

実装スニペットは `skills/design/animate-css/SKILL.md`、`skills/design/hover-animations/SKILL.md`、Neonのアニメーション集（`skills/common/neon-animation-registry/SKILL.md`）を先に見る。

## 4. 状態設計（実装UIで最も落ちる部分）

ボタン・リンク・入力欄・カードは、静止画1状態だけ作って終わりにしない。

| 状態 | 要件 |
|---|---|
| default | 何ができるか一目でわかる |
| hover | 変化は明確に。ただし要素の大きさは動かさない（レイアウトが揺れる） |
| focus-visible | **outlineを消したまま放置しない。** 消すなら代替の枠・影を必ず与える |
| active | 押した瞬間の手応え（1〜2px沈む・色が濃くなる） |
| disabled | 押せない理由が近くに書いてある。コントラストは落としすぎない |
| loading | 押した直後に反応。二重送信を止める |
| empty | 「データがありません」で終わらせず、次の行動を示す |
| error | 何が・なぜ・どう直すかを該当箇所の隣に日本語で |
| success | 完了したことと、次に何が起きるか（例「翌営業日までに返信します」） |

**AIっぽく見える実装を避ける**: ピル型ボタン＋グロー影、円形アイコンチップ、意味のないグラデーション枠は使わない（プロジェクト共通ルール）。

## 5. フォームUX（問い合わせ・予約の離脱を左右する）

- 項目は最小限。任意項目は消すか「任意」と明示する。
- ラベルは常時表示。placeholderをラベル代わりにしない（入力すると消える）。
- 入力形式を先に示す（例: 08012345678／ハイフンなし）。
- `type` を正しく使う（email / tel / date）。モバイルのキーボードが変わる。
- `autocomplete` を付ける（name / email / tel / postal-code）。
- エラーは送信後にまとめて出さず、フィールド単位でその場に出す。
- 送信ボタンの文言は「送信」より「無料で相談する」。何が起きるかを書く。
- 送信後の受け皿（サンクス表示・次のアクション）を必ず用意する。

## 6. アクセシビリティ最低ライン

納品物として最低限守る項目。ここを外すと「作りが雑」と判断される。

- `<html lang="ja">` がある。
- 見出しは h1 → h2 → h3 の順で飛ばさない。h1はページに1つ。
- 画像に alt。装飾画像は `alt=""` を明示。
- キーボードのTabだけで主要導線をたどれ、フォーカス位置が見える。
- ピンチズームを禁止しない（`user-scalable=no` を書かない）。
- コントラスト比 AA（3-3参照）。
- 色・形・位置だけで情報を伝えない。

## 7. 実測監査（Playwright）

HTML実装のページを実際にChromiumで開き、測れる項目を機械的に検査する。

```bash
# リポジトリルートから実行（ローカルHTMLでも公開URLでも可）
node skills/design/uiux-design/scripts/uiux-audit.mjs portfolio/<slug>/lp/index.html --out exports/reviews/<slug>-uiux.md

# モバイルだけ / PCだけ
node skills/design/uiux-design/scripts/uiux-audit.mjs https://example.vercel.app --viewport mobile

# JSONも保存（差分比較や再監査に使う）
node skills/design/uiux-design/scripts/uiux-audit.mjs <target> --out report.md --json report.json
```

既定でモバイル(390×844)とPC(1440×900)の両方を検査し、遅延読み込みを出すため一度最下部までスクロールしてから測る。
リポジトリ直下の `playwright`（devDependency）とChromiumを使う。未導入なら `npm install` → `npx playwright install chromium`。

**検査項目**

| カテゴリ | 内容 |
|---|---|
| アクセシビリティ | コントラスト比（背景画像・半透明スクリムの重なりを合成して算出）、alt、lang、ズーム禁止、Tab移動時のフォーカス可視性（実測） |
| タイポグラフィ | 文字サイズ、行間、1行の文字数、サイズ種類数 |
| モバイルUX | タップ領域、入力欄のフォントサイズ |
| レイアウト | 横スクロールの発生と原因要素 |
| フォームUX | ラベル欠落、type、autocomplete |
| 情報設計 | h1、見出しレベルの飛び、title、description、og:image |
| 反復 | 書体数、文字サイズ種類数、余白のグリッド逸脱率、中央揃えの比率 |
| モーション | transitionの長さ、prefers-reduced-motion対応 |
| コンバージョン | CTA数とファーストビュー内の有無、追従CTAの有無 |

**重大度の扱い**

- 🔴 重大 … 直してから納品する。終了コード1を返すので `&&` で繋ぐ工程に組み込める。
- 🟡 要改善 … 意図があるなら残してよいが、理由を説明できること。
- 🔵 参考 … 判断材料。件数の多さ自体が設計のばらつきを示す（例: 文字サイズ23種類）。

**誤検知しやすい箇所**（レポートを鵜呑みにしない）

- 背景画像の上の文字は「明るい背景／暗い背景の両極」で評価している。実画像で目視確認する。
- 12〜14pxのラベル・注釈は日本語LPの常用域。本文かラベルかを見て判断する。
- 装飾用の小さな要素がタップ領域として拾われることがある。

### スワイプLPの場合

`skills/design/swipe-lp-creator/SKILL.md` のスワイプ型は1画面1カード構成のため、`--viewport mobile` のみで監査し、横スクロール検査の結果は構造（横並びカルーセル）を踏まえて読む。

## 8. 目視チェック（機械が測れない部分・納品前必須）

1. **5秒テスト**: ファーストビューを5秒見て閉じ、「誰の何のサービスか」「次に何をすればいいか」を言えるか。
2. **視線の順路**: 画面を薄目で見て、目立つ順に1→2→3と番号を振れるか。CTAが3位以内に入っているか。
3. **1画面1メッセージ**: スクロールを止めた各位置で、伝えたいことが1つに絞れているか。
4. **グループの境界**: セクションの切れ目が余白で分かるか（線や色で無理やり区切っていないか）。
5. **前後の整合**: 広告・サムネの訴求とファーストビューの訴求が同じか。
6. **信頼の材料**: 数字・実績・顔・所在地・料金の内訳のうち、その業種で必要なものが揃っているか。
7. **文言の主語**: 「私たちは〜を提供します」ではなく「あなたは〜できます」になっているか。
8. **スマホ実機**: 親指の届く範囲にCTAがあるか、追従バーが本文を隠していないか。
9. **セクション画像の裾**: 次セクションの内容が画像下部に写り込んでいないか（画像LP固有の頻出ミス）。
10. **文字の乗る場所**: 画像上の文字が、被写体の顔や重要部分に被っていないか。

## 9. 診断・改善提案としてのアウトプット

既存サイトの診断案件では `references/review-template.md` の形式で書く。守る順序は
**現状の事実 → それが起こす不利益 → 改善案 → 期待できる変化**。
「余白が足りません」で止めず、「本文と見出しの間隔が同じ12pxのため、どの見出しがどの段落に属するか判別に時間がかかる。見出し上を32pxに広げると視線が段落単位で止まる」まで書く。

指摘は多ければよいものではない。重大→要改善の順に、**影響の大きい5〜8件に絞る**。
